Production incidents I've handled, and what they taught me

Twelve real issues from running AWS, Kubernetes and on-prem Linux for 20+ products. Each one follows the same path: symptoms, investigation, root cause, fix and lessons. Each also has a 60-second version and the follow-up questions engineers usually ask.

Company names, hosts and account details are removed. The numbers are real.

cat approach.md

How I work an incident

  1. Detect and scope

    What is broken, for whom, since when. Check dashboards and alerts, and agree on one incident channel.

  2. Stabilize first

    Roll back, scale, fail over or replace the bad pod. Users first, root cause second.

  3. Find the first error

    Build a timeline. The loudest error is often an amplifier, not the cause.

  4. Prove the root cause

    Reproduce it, or show it with metrics, logs or the exact line of code. No guessing.

  5. Fix and prevent

    Ship the permanent fix plus a guardrail: an alert, a test, a policy or a runbook.

  6. Write it down

    A blameless review with numbers, so the next person can recognize the pattern in minutes.

#01kuberneteskarpenterawsimpact: ~7 min down per spot reclaim

Spot reclaims took pods down for 7 minutes: interruption handling was never wired

TL;DRKarpenter had an SQS interruption queue configured, but no EventBridge rules sent events to it. It never received the 2-minute spot warning, so nodes died without a drain, and an EBS volume stayed attached to the dead node for about 6 minutes.

Symptoms

  • A single-replica StatefulSet with an EBS volume, running on spot capacity, "restarted on its own" and stayed down about 7 minutes each time.
  • In the same cluster, a single-replica real-time worker was evicted in the middle of a live session by Karpenter consolidation (Underutilized).

Investigation

  1. Pod events: the new pod was stuck in ContainerCreating. The VolumeAttachment of the ReadWriteOnce volume still pointed at the dead node until Kubernetes force-detached it about 6 minutes later.
  2. aws ec2 describe-instances showed Server.SpotInstanceTermination and the spot request said instance-terminated-no-capacity. It was a reclaim, not a crash.
  3. Karpenter logs had no disrupting node(s) line (that line marks consolidation). There was only tainted node, after the instance was already gone.
  4. Karpenter was configured with an interruption queue and the queue existed, but aws events list-rule-names-by-target for it returned nothing.

Root cause

Interruption handling was half-configured: queue yes, EventBridge rules no. Without the 2-minute notice, Karpenter could not cordon, drain and launch a replacement early. The volume detach delay turned a short restart into a 7-minute outage.

Fix

  • Created the 5 EventBridge rules from Karpenter's reference template (spot interruption, rebalance recommendation, scheduled change, instance state change, capacity reservation interruption) with the queue as target. The queue policy allows EventBridge and denies non-TLS access, and retention is set to 300 seconds.
  • Verified with Karpenter's own metric karpenter_interruption_received_messages_total (CloudWatch SQS metrics lag behind) and kept a rollback script.
  • Moved single-replica, latency-sensitive workloads to an on-demand NodePool with karpenter.sh/do-not-disrupt, plus the pool's toleration (without it, pods stay Pending).

Lessons

  • PDBs and do-not-disrupt only stop voluntary disruption (consolidation, drift). Against a spot reclaim, only the interruption warning, extra replicas or on-demand capacity help.
  • Tell consolidation and reclaim apart in the logs before choosing a fix.
  • Verify an integration by its metrics, not by the presence of a config value.
In 60 seconds + deep-dive Q&A
Situation
Production pods on spot nodes were going down for about 7 minutes at random times.
Task
Find out why and stop the outages without giving up the spot savings.
Action
Traced the pod timeline to a spot reclaim and an EBS volume stuck on the dead node. Found that Karpenter's interruption queue had no EventBridge rules, wired the 5 rules and verified them with Karpenter metrics. Moved single-replica workloads to on-demand capacity with do-not-disrupt.
Result
Karpenter now gets the 2-minute warning and drains nodes ahead of time. The 7-minute outages on spot reclaims stopped.
What is the difference between a spot interruption and consolidation?
An interruption is AWS taking the capacity back with a 2-minute warning; it is involuntary. Consolidation is Karpenter removing or replacing nodes to save money; it is voluntary and respects PDBs and do-not-disrupt.
Why did the pod take 7 minutes instead of 30 seconds?
The volume was ReadWriteOnce and its attachment still referenced the terminated node, so the new pod could not mount it until the attach/detach controller force-detached it after about 6 minutes. A graceful drain releases the volume immediately.
How would you make a stateful service tolerate spot?
Multiple replicas spread across AZs with a PDB, interruption handling wired, graceful shutdown (preStop hook, enough grace period). Or keep it on on-demand capacity if it cannot be replicated.
What is the downside of do-not-disrupt?
It also blocks drift and expiry, so the node is not patched or right-sized. Use it only for workloads that truly cannot move.

#02reliabilitycapacitycontainersimpact: translation dropped 7 times in 15 min

A live-translation service failed in its biggest meeting yet

TL;DRA 7-person, 4-language meeting (21 translation branches) pushed the agent past its 2-CPU limit. The reconnect storm then hit the speech-to-text vendor's limit of 10 concurrent streams, a busy-loop bug froze the worker, and a shell as PID 1 swallowed SIGTERM, so old pods never drained.

Symptoms

  • Translation latency rose from 7–11 s to 34–45 s. Then the media server (SFU) closed the agent with NEGOTIATE_FAILED, and the agent was killed and replaced 7 times in 15 minutes. People moved to a smaller room, where it worked.
  • Kubernetes showed the pod as Ready the whole time.

Investigation

  1. Built a timeline from the logs. The first two drops had no vendor errors at all, so this was pure overload. The first HTTP 429 from the vendor came only after the restart, when the old and new pods held streams at the same time.
  2. cgroup stats showed CFS throttling in 16–62% of periods against a 2-core limit. The room needed about 2.8 cores. The SFU host itself was fine (15–30% CPU).
  3. The vendor's concurrency API showed an organization-wide cap of 10 streams, shared by every environment and service that used the same key.
  4. Reproduced locally: after the server closed the websocket, the STT plugin's receive loop kept getting an already-closed message without awaiting. It spun without yielding the asyncio event loop, the job froze with zero log lines, and the worker killed it after 60 seconds. Upstream had already fixed it.
  5. The container started with sh -c "python …", so PID 1 was the shell and it ignored SIGTERM. Python never drained; the old pod kept accepting new jobs for the whole 210-second grace period and was then killed.
  6. The health check only tested a TCP port held by the parent process, so the pod looked healthy while every meeting on it was dead.

Root cause

Load above the CPU limit was the trigger. Three latent bugs (a shared vendor cap, a busy-loop on a closed socket, PID 1 not forwarding signals) turned one overload into a crash loop. They had never shown up because no earlier meeting was this large; the previous record was 6 people and 3 languages.

Fix

  • A fan-out redesign: each speaker is transcribed once and the turn is replayed to every language branch (one STT stream per speaker), with an overload guard and a per-room cost ceiling. It rolled out in stages behind one flag; stage 2 was live in production the next day.
  • Signal and plugin fixes: exec-form entrypoint (or tini) so SIGTERM reaches Python and the worker drains, a backport of the upstream plugin fix, and CPU request and limit sized from measurement.
  • Agent dispatch deduplicated per room, with jitter. In an earlier incident, 5 browsers re-requested an agent within 240 ms, which opened about 52 STT streams in 14 seconds.
  • Recommended: separate vendor keys per environment, a health check based on active sessions instead of a port, and load tests sized as speakers × languages.

Lessons

  • At a new peak, latent bugs line up. Load-test the worst case, not the average.
  • Find the first error. Here the 429s were an amplifier, not the cause.
  • PID 1 must handle signals, or rolling updates kill sessions instead of draining them.
  • A health check must test what users need, not just an open port.
In 60 seconds + deep-dive Q&A
Situation
A live speech-translation service failed during its largest meeting so far: 7 people, 4 languages.
Task
Restore service, find the root cause and make large meetings safe.
Action
Rebuilt the timeline and showed that overload came first and the vendor 429s came later. Measured CPU throttling, found the shared 10-stream cap, reproduced a busy-loop bug in the STT plugin and found PID 1 swallowing SIGTERM. Drove a fan-out redesign that transcribes each speaker once.
Result
Stage 2 of the redesign was live in production the next day, together with a clear fix list for signals, the plugin and quotas, and a load-test model based on speakers × languages.
How did you know the 429s were not the cause?
Timestamps. The first two disconnects had no 429 at all. The first 429 came after the restart, when two pods overlapped.
What is CFS throttling and how do you see it?
It is the kernel's CPU bandwidth control: a container that uses up its quota in a 100 ms period is paused until the next period. Check cpu.stat in the cgroup or container_cpu_cfs_throttled_periods_total.
Why does sh -c as PID 1 break graceful shutdown?
PID 1 has no default signal handlers and the shell does not forward SIGTERM to its child. The app never hears it and is killed after the grace period. Use exec form, exec in the script, or an init such as tini.
How do you stop a thundering herd of reconnects?
Deduplicate on the server (one in-flight request per room with a short TTL) and add jitter and exponential backoff on the clients.

#03observabilityopensearchkubernetesimpact: log search outages · disk 80%

OpenSearch went red, and a retention policy had silently failed for months

TL;DRThe production retention policy was rejected with HTTP 400 at deploy time, but the init script printed success. Production logs were never deleted, shards piled up, and every node move caused a long, heavy recovery.

Symptoms

  • Dashboards returned "internal server error": the parent circuit breaker tripped at 99% of a 2 GB heap after the pod moved to a new node and reloaded about 3,650 primary shards.
  • Later the cluster went RED twice in 21 hours after the pod moved; each recovery took 13–15 minutes.

Investigation

  1. _cluster/allocation/explain said can_allocate: yes and throttled: RED meant a slow recovery, not data loss.
  2. The policy init script logged "done (0)", but $? came from echo, not from curl. The real response, in a log file inside the pod, was HTTP 400: two ISM templates with overlapping index patterns cannot share the same priority.
  3. ISM templates attach only when an index is created, so even a fixed policy would not manage existing indices. Production indices were 178 days old.
  4. Shard math: 33 GB over 2,332 shards is about 14 MB per shard. Daily indices for every small service created thousands of tiny shards; 40 small families held 65% of the shards but only 4% of the data.
  5. Recovery speed was limited by default throttles (4 concurrent initial primary recoveries), not by bandwidth: 33 GB at 40 MB/s is about 14 seconds.

Root cause

An unchecked API call in a postStart hook plus a priority collision left production with no retention, and one daily index per service multiplied the shard count. A single-node cluster on movable nodes made every move a full recovery.

Fix

  • Gave each policy a unique priority, attached existing indices with _plugins/_ism/add and purged 2,000 old indices (71 GB). Disk went from 80% to 38% and shards from 4,947 to 2,683.
  • Raised the heap from 2 to 3 GB and set replicas to 0 on this single-node cluster, which made it GREEN with no phantom replicas.
  • Raised recovery concurrency (initial primaries 4 → 32, concurrent recoveries 8, larger chunk and bandwidth limits). Recovery now goes from 64% to 99.4% in under 2 minutes instead of about 15.
  • Protected the pod from consolidation, created the first S3 snapshot repository (with IRSA), and changed the RED alert from for: 5m to 15m so a normal recovery no longer pages anyone.

The mistake I tell in interviews: a wildcard _ism/add/*dev* also matched index aliases, so a 14-day policy deleted 132 small dev indices (214 MB). Since then I run _cat/aliases before any wildcard write.

Lessons

  • Check the result, not the exit code of a different command. Read the real log.
  • Plan shards: use rollover or monthly indices for small services. With monthly indices, min_index_age counts from index creation, so retention must be at least 60 days or fresh data gets deleted.
  • Recovery throttles are the cheapest lever for recovery time.
  • No snapshots means no backup, even for logs.
In 60 seconds + deep-dive Q&A
Situation
Our logging cluster went red again and again, and search returned errors.
Task
Stabilize it and find out why it was so fragile.
Action
Proved RED was a throttled recovery. Found that the retention policy had been rejected for months while the script reported success. Fixed the priorities, attached old indices, purged 71 GB, and tuned heap, replicas and recovery throttles. Added snapshots.
Result
Disk 80% → 38%, shards down 46%, recovery under 2 minutes instead of about 15, and no more false alerts.
Why are too many small shards bad?
Every shard costs heap and file handles and is recovered on its own, and the cluster state grows. Aim for tens of GB per shard, use rollover and merge small indices.
Why did fixing the policy not clean the old indices?
ISM templates bind at index creation. Existing indices need an explicit add or change_policy call.
How would you make this cluster resilient?
At least 3 nodes on stable capacity with replicas, snapshots to S3, rollover-based ISM, and alerts on heap, disk watermarks and unassigned shards.
Tell me about a mistake you made.
The alias wildcard above: small blast radius in dev, and it changed how I run every wildcard operation.

review: shards & heap · circuit breakers · ism/ilm · disk watermarks · snapshot repositories

#04linuxdockerstorageimpact: session replay silently broken for ~7 weeks

A self-hosted analytics stack crash-looped 7,279 times while docker ps said "Up"

TL;DRThe object store hit its default limit of 8 volumes and its only volume went read-only. Uploads timed out, the ingestion service exited with code 0, and restart: always hid the loop. 33 GB of ZooKeeper logs and exhausted CPU credits made it worse.

Symptoms

  • Session replays stopped arriving and ingestion had gaps. Root disk was at 92%, CPU steal at 51% and load at 10.7.
  • docker ps showed every container as Up.

Investigation

  1. docker inspect --format '{{.RestartCount}}' returned 7,279, about one restart every 7 minutes. Exit code 0 plus restart: always made the crash loop invisible.
  2. Logs: "S3 upload timed out after 120000ms", then an unhandled promise rejection and a shutdown. Each restart also killed every other consumer in that service.
  3. The object store (SeaweedFS) said "No writable volumes". The volume server's default of 8 slots was full, and the only bucket volume (31.4 GB) had passed the 30 GB size limit, so it was read-only. A bigger disk did not help: the limit was slots, not space.
  4. ZooKeeper autopurge had been disabled from day one, leaving 33 GB of transaction logs.
  5. The burstable instance used standard credits with a balance of 0.17, so steal was 51% and CPU was pinned at the 40% baseline for 7 days.

Root cause

Three unsafe defaults (8 volume slots, ZooKeeper autopurge off, standard CPU credits) plus a process that exits with code 0 on a fatal error.

Fix

  • Raised the volume slots to 30 and lowered the volume size limit to 8 GB, so new writable volumes appeared. After a restart of the service, restarts stayed at 0. Added a 30-day TTL for recordings.
  • Ran ZooKeeper cleanup live and enabled autopurge: disk 92% → 54% (36 GB freed) with no restart.
  • Switched the instance to unlimited credits (immediate, no reboot): steal 0%, load 2.46.
  • Later moved the main object storage to Amazon S3.

Lessons

  • Alert on restart counts; "Up" is not "healthy".
  • Exiting with code 0 on a fatal error is a bug.
  • Know the defaults of every stateful component you host.
  • On burstable instances, watch the CPU credit balance; a new instance type does not help if the credit mode stays standard.
In 60 seconds + deep-dive Q&A
Situation
A self-hosted product-analytics stack looked up, but session replay had been dead for weeks.
Task
Find the cause and restore ingestion without losing data.
Action
Found 7,279 hidden restarts and traced them to an object store out of volume slots. Freed 36 GB of ZooKeeper logs live and fixed CPU credit starvation.
Result
Restarts 0, disk 92% → 54%, CPU steal 51% → 0%, replay working again.
How do you detect a crash loop that Docker hides?
Track the restart count (docker inspect, cAdvisor, or kube_pod_container_status_restarts_total in Kubernetes) and alert on its rate.
What is CPU steal?
Time the hypervisor did not give your vCPU. On burstable instances it often means the CPU credits ran out.
Why did adding disk not fix it?
The error was about writable volume slots. Each volume has a size cap and the server had a maximum number of volumes.

review: docker restart policies & exit codes · burstable credits · zookeeper maintenance · alerting on restarts

#05securitymysqlrecoveryimpact: production data at risk · recovered with no data loss

A database behind a public load balancer: point-in-time recovery and lock-down

TL;DRA legacy setup left a MySQL instance running in Kubernetes reachable from the internet through a public Network Load Balancer, and its data had to be recovered. We restored it from EBS snapshots plus binary logs with no data loss, then removed the public path.

What we found

  • The database Service was of type LoadBalancer, backed by an internet-facing NLB, with security groups wider than needed. It was a leftover from an old setup.

Recovery: point-in-time restore

  1. Contain first: switched the Service to ClusterIP and tightened the security groups, so nothing new could reach the database.
  2. Restore the data volume from the last good EBS snapshot.
  3. Replay the binary logs from the snapshot's position up to just before the bad change (mysqlbinlog --stop-datetime or --stop-position).
  4. Verify row counts and application behaviour, then put it back in service.

Hardening I drove afterwards

  • Closed internet-exposed database and admin ports across the AWS estate; access now goes through a managed prefix list.
  • Cut public S3 buckets from 15 to 2, and added DNS Firewall alerting and VPC Flow Logs.

Lessons

  • Snapshots plus binary logs give point-in-time recovery, but only if binlog retention covers the gap and restores are tested.
  • In Kubernetes on AWS, a Service of type LoadBalancer is internet-facing unless you mark it internal. Review every one.
  • Audit security groups for 0.0.0.0/0 on database and admin ports continuously, not once.
In 60 seconds + deep-dive Q&A
Situation
A legacy MySQL in Kubernetes was reachable from the internet, and its data needed recovery.
Task
Recover with no data loss and close the hole.
Action
Contained first, restored from EBS snapshots, replayed binary logs to the right point, verified, then moved the Service to ClusterIP and locked down the security groups.
Result
Full recovery with no data loss. Later I led a wider cleanup of open ports and public buckets.
How does point-in-time recovery work for MySQL?
Restore a full backup or snapshot, then replay the binary logs from the backup's binlog position up to the target time or position.
What do you do first in a suspected breach?
Contain (cut access, rotate credentials), preserve evidence, find the scope with logs (VPC Flow Logs, database logs), then recover and harden.
How do you prevent this class of issue?
Internal load balancers by default, admission policies that block public load balancers for databases, regular security-group audits, private endpoints and least privilege.

#06networkingaws nlbkubernetesimpact: clients could not reconnect for ~2 min

RabbitMQ clients timed out after node churn: cross-zone load balancing was off

TL;DRA broker pod drained during a spot reclaim. Its NLB had cross-zone load balancing disabled and the drained pod was the only target in its AZ, so every client that resolved that AZ's IP got TCP timeouts while the other AZ was healthy.

Symptoms

  • A consumer lost its broker in the middle of a live event, and its reconnects timed out instead of failing over.

Investigation

  1. The time matched a spot reclaim. Karpenter drained the node, and the broker's preStop rabbitmq-upgrade drain put it into maintenance mode (CONNECTION_FORCED). It was gone for 67 seconds.
  2. The NLB had cross-zone off: DNS returns one IP per AZ, and each IP only reaches targets in its own AZ. AZ-a had a single broker pod, and its per-AZ HealthyHostCount dropped to 0 for about 2 minutes while AZ-c stayed healthy.
  3. History: the broker pods had changed nodes 826 times in 3 months (about 10 a day), half from spot reclaims and half from consolidation. Kubernetes events last only an hour, so I rebuilt the history from CloudTrail (BidEvictedEvent plus the volume's AttachVolume calls).
  4. Checked where connections land by opening N connections to one NLB IP and comparing /proc/net/tcp6 in each pod. On dual-stack sockets IPv4 shows up as ::ffff:, so reading only /proc/net/tcp shows zero connections.

Root cause

Zonal NLB routing plus an uneven pod spread: one AZ had a single target, so draining it blackholed that AZ's IP.

Fix

  • Enabled cross-zone load balancing on the target groups. Connections to the AZ-a IP now spread across all pods: before 9/0/0, after 5/1/3. Rollback is one CLI call.
  • Recommended: clients reconnect with backoff and try other endpoints; spread broker pods evenly across AZs.

Lessons

  • NLB cross-zone is off by default, and then each AZ IP is its own failure domain.
  • Brokers on spot see constant churn; design clients for it.
  • When Kubernetes events are gone, CloudTrail and per-AZ load balancer metrics still tell the story.
In 60 seconds + deep-dive Q&A
Situation
A message consumer lost its broker mid-event and could not reconnect for two minutes.
Task
Explain the timeouts and stop them.
Action
Tied the drop to a spot drain, found cross-zone disabled with a single target in one AZ, rebuilt 3 months of churn from CloudTrail and tested how connections spread across pods.
Result
Turned on cross-zone; any NLB IP now reaches healthy pods in every AZ.
What does cross-zone load balancing change?
With it on, each load balancer node can send traffic to targets in any enabled AZ; with it off, only to its own AZ. It is on by default for ALB and off for NLB, and inter-AZ traffic costs apply.
Why did clients time out instead of retrying another IP?
They resolved once and kept one IP. A TCP SYN to an AZ with no healthy target just times out.
How would you run RabbitMQ on Kubernetes more safely?
The Cluster Operator with 3 replicas across AZs, quorum queues, a PDB, stable capacity, and clients with reconnect and backoff.

#07networkingaws albwebsocketimpact: periodic "lag" and 5-second reconnects

WebSocket clients dropped at exactly 60 seconds: browser throttling met the ALB idle timeout

TL;DRBackground browser tabs slowed the client's message loop to about one message per minute. The ALB closes idle connections after 60 seconds, so when a gap reached 60.0 seconds, the connection died.

Symptoms

  • Players reported that "the game server is lagging". Server p95 was under 35 ms, database CPU was 2–3%, and there were almost no slow requests.

Investigation

  1. Ruled out the server and the database first: p95, CPU and slow logs were all healthy.
  2. Looked at session removals for real users: 2–5 drops per 15 minutes, each taking about 5 seconds to reconnect.
  3. Client message gaps grew 30 s → 57 s → 59 s → 60.0 s, then the connection dropped, always at exactly 60 seconds and only with the tab in the background. Chrome's intensive timer throttling slowed the WebGL loop to about one message per minute.
  4. The server's own idle timeout was 120 seconds, so the server was not closing the connection. The ALB idle timeout was 60 seconds, and ALB access logs showed the wss connection closing within 1 ms of the server's "remove user".

Root cause

The load balancer's idle timeout was shorter than the client's worst-case gap between messages.

Fix

  • Raise the ALB idle timeout to 120–180 seconds and add a server-side ping (or protocol heartbeat) under 60 seconds that does not depend on the client's throttled loop. Make reconnects seamless.

Lessons

  • Not every "lag" is the server or the database; measure before tuning.
  • Every proxy in the path has an idle timeout (ALB 60 s by default, NGINX proxy_read_timeout 60 s). WebSockets need heartbeats below the smallest one.
  • Browsers throttle timers in background tabs.
In 60 seconds + deep-dive Q&A
Situation
Users reported lag while every server metric was green.
Task
Find the real cause.
Action
Ruled out the server and the database, then matched client message gaps to disconnects and the exact 60.0 seconds to the ALB idle timeout, confirmed with ALB access logs.
Result
Root cause proven with logs; the fix is one setting plus a heartbeat.
Where can a WebSocket be cut in AWS?
The browser, a CDN, ALB/NLB idle timeouts, ingress or proxy timeouts, and the application's own idle timeout.
Should the ping come from the client or the server?
The server (or protocol ping frames), because background tabs throttle client timers.
How did you prove it was not the server?
The server's idle timeout was 120 seconds, but drops happened at 60.0 seconds, the ALB value, and ALB logs closed the connection at that exact moment.

review: websocket keepalive · alb idle timeout · browser timer throttling · alb access logs

#08linuxkernelci/cdimpact: CI failing · hard resets needed

An on-prem build server froze: kernel RCU stalls, not CPU or memory

TL;DRStarting and stopping containers needed an expedited RCU grace period, but one CPU core sat in a deep idle state and never answered. Hundreds of processes queued in uninterruptible sleep behind one kernel lock.

Symptoms

  • Jenkins jobs failed with "docker run … Timeout after 180 seconds".
  • SSH accepted connections but could not run commands, while running containers kept serving.
  • It came back after 2.5 days, then 4 days, then 2 days, and finally 5 minutes after a reboot.

Investigation

  1. Load average was 231 while only 16 of 125 GB RAM was used and the disk had plenty of space: not a resource problem.
  2. ps -eo stat | grep -c ^D returned about 240 processes in uninterruptible sleep (D state), mostly runc.
  3. dmesg: "rcu_preempt detected expedited stalls", and the NMI backtrace showed the stalled CPU idling in intel_idle.
  4. Kernel stacks: the first stuck task waited in synchronize_rcu_expedited (mount namespace release when a container exits) while holding the lock, and every later runc queued behind it.

Root cause

A kernel and CPU interaction: expedited RCU grace periods never completed because a core in a deep C-state did not respond. This is a known class of issue on this desktop CPU generation.

Fix

  • Workaround that shipped: moved the build jobs to another on-prem node, where builds were also faster (4m33s vs about 8 minutes). Added the agent prerequisites (git-lfs and the AWS CLI on the host, because those steps run outside the build container) to a checklist.
  • Recommended mitigations: kernel.rcu_normal=1, the boot parameter intel_idle.max_cstate=1, and a BIOS and microcode update.

Lessons

  • High load with idle CPUs and many D-state processes means tasks are blocked in the kernel. Read dmesg and the kernel stacks.
  • A reboot that helps for less time each round is not a fix.
  • Find the first error: at the end of the log, a credential-type error was hiding "aws: not found".
In 60 seconds + deep-dive Q&A
Situation
Our on-prem CI host kept freezing and builds failed.
Task
Find out why and keep CI running.
Action
Showed it was not CPU, RAM or disk, found about 240 D-state tasks behind an expedited RCU stall, moved the builds to another node and proposed kernel and BIOS mitigations.
Result
CI was green again, and builds got faster (4m33s vs about 8 minutes).
What is D state?
Uninterruptible sleep, usually waiting for I/O or a kernel lock. kill -9 does not work on it, and it counts towards the load average.
What is RCU?
Read-Copy-Update, a kernel synchronization mechanism: writers wait for a grace period until all readers are done. Expedited grace periods force this with interrupts to every CPU.
How do you debug a host where you cannot run new commands?
Use a session that is already open or the console, dump blocked tasks with echo w > /proc/sysrq-trigger, and read the persistent journal after the reboot.

#09databasemongodbperformanceimpact: 1–2.5 s requests · database at 100% CPU

"The game lags": MongoDB collection scans on a small instance

TL;DRIndex annotations in the code were never applied, because auto-index creation was off and there was no migration. Hot queries scanned 133,000 to 269,000 documents.

Symptoms

  • Players reported stutter during tournaments. Slow requests clustered at even minutes, while the app pod used about 0.1 of its 1 CPU.

Investigation

  1. The app pod was healthy. The database host (a t3.small) went from 2% CPU to 40–48% on average, with 99.8% peaks once play started, and its CPU credits were falling.
  2. The mongod slow log showed 30–48 seconds of query time per minute, almost all on one collection with 269,000 documents:
    • find {eventId} was a COLLSCAN, although the code declared a unique index on that field.
    • find {stream, sourceEventId} used only a prefix of another index and examined 133,000 documents (1–2.5 s).
  3. Spring Data auto-index creation was disabled and the collection had no create migration, so the annotations never became indexes.
  4. A 7-day TTL index deleted nothing: 214,000 of 220,000 rows stored the timestamp as a number, and TTL only works on Date values.
  5. A week later, a second hotspot: the users collection had only the _id index, and a case-insensitive email lookup (with a collation) ran once per seat per request. Bots polling every second pushed the database to 100% CPU.

Root cause

Missing indexes in production, plus per-request lookups multiplied by polling.

Fix

  • Gave the team that owns the schema an exact fix: a unique index on eventId, a compound index on {stream, sourceEventId}, an email index with the same collation as the query, a backfill that converts timestamps so the TTL works, and caching of user lookups. It went in as their migration.

Lessons

  • ORM index annotations are not a migration. Manage indexes explicitly.
  • A TTL index needs a Date field; a collation query needs an index with the same collation.
  • Check the database slow log before scaling the application.

#10kubernetesapplicationdebuggingimpact: ~50% of admin requests failed

Half the requests failed: a poisoned in-process cache in one long-lived pod

TL;DRA UI library cached a schema map in process-global memory, keyed only by collection name. If the first request that built it was unauthenticated, the map was built from a stripped config and stayed broken until restart. With two replicas behind an ALB, about half of the requests hit the bad pod.

Symptoms

  • A CMS admin page "sometimes shows data, sometimes not". Locally, everything worked.

Investigation

  1. Pod logs had a TypeError during server-side rendering, in minified code. I de-minified it by downloading the exact package versions (npm pack) and searching them: the client field schema map was missing an entry that the server map had.
  2. Found the cache: stored on global, keyed only by the collection slug, alive for the life of the process.
  3. Evidence: the oldest pod (4 hours 23 minutes) had logged 69 errors, freshly started pods had logged 0. Same image, same environment, same database.
  4. Reproduced it with a script: if the first build was authenticated, the map had 17 entries and worked; if it was unauthenticated, it had 3 entries and crashed.

Root cause

A cache poisoned by the first unauthenticated request, plus round-robin over two replicas, gave about 50% failures.

Fix

  • Mitigation: scaled to one replica and restarted the rollout through Git. ArgoCD self-heal reverts kubectl scale, and scaling down removes the newest pod first, which keeps the bad one, so a rollout restart was required.
  • Root fix: a pnpm patch so an unauthenticated config never reads or writes the shared cache. The Dockerfile must also copy patches/ and pnpm-workspace.yaml, or the patch silently does not apply. Upgrading the library did not help; the latest version had the same code.

Lessons

  • "Sometimes" plus multiple replicas: look for per-pod state.
  • Process-global caches need complete keys (who, what, which version).
  • Verify that a patch is really inside the image.

#11karpenteraws organizationsimpact: no new nodes · CI stuck

Autoscaling stopped cluster-wide: an organization SCP denied ec2:RunInstances

TL;DRA service control policy at the AWS Organizations level blocked Karpenter from launching instances. All 7 NodePools used one EC2NodeClass, so the whole cluster lost scale-out at once.

Symptoms

  • Pods stayed Pending ("0/14 nodes are available … untolerated taints") and no NodeClaims were created. Existing nodes kept running.

Investigation

  1. No NodeClaims meant Karpenter was not even trying; the NodePools were Ready=False.
  2. The EC2NodeClass conditions said RunInstancesAuthCheckFailed: not authorized to call ec2:RunInstances because of a service control policy.
  3. All 7 NodePools pointed at that single EC2NodeClass.

Root cause

A guardrail outside the cluster (an SCP), plus a shared EC2NodeClass as a single point of failure.

Fix

  • Pinned CI to a pool that still had capacity, escalated the SCP to the organization admins with the exact evidence, and documented a one-line health check: kubectl get ec2nodeclass default -o jsonpath='{.status.conditions}'.

Lessons

  • When nodes do not appear, check NodeClass and NodePool conditions before digging into the scheduler.
  • Alert on NodePool and NodeClass Ready=False.
  • The erosion is silent: nothing breaks until a node needs replacing, and then it cannot be replaced.

#12linuxmemorywebrtcimpact: a streaming server unresponsive for ~11 hours

One viewer opened 1,247 WebRTC sessions and froze a streaming server

TL;DRA client in a retry loop opened about one session every 3 seconds. Memory leaked inside the media server until the kernel was thrashing the page cache. Nothing was killed, so nothing restarted.

Symptoms

  • SSM commands were undeliverable, the instance status check was impaired, network out was 0 and CPU was about 10% (iowait).
  • A ping alert fired for 11 hours, but nobody acted on it.

Investigation

  1. Thrashing signature: EBS read operations went from 700 per hour to 4.4 million per hour while writes stayed flat; the page cache dropped from 1,040 MB to 38 MB; there was no OOM kill.
  2. Container logs survived the reboot: 1,268 WebRTC sessions that day, 1,247 of them from one viewer, each lasting about 2 seconds. It was a client reconnect loop caused by a broken H.264 stream.
  3. Memory kept climbing after the churn stopped, so closed sessions were not being freed inside the media server.

Root cause

Unbounded session churn from one client, a leak in the media server, and no memory safety net on the host.

Fix

  • Hardened both the dev and prod hosts: swap plus earlyoom (which prefers killing the media server over system services), min_free_kbytes and kernel.panic.
  • Added node_exporter with per-container memory metrics, CloudWatch alarms with automatic reboot and recovery, logs shipped to OpenSearch, and a metric for readers per stream.

Lessons

  • "No OOM kill" does not mean healthy; thrashing can freeze a box for hours.
  • An alert nobody watches is not monitoring.
  • Rate-limit sessions per client.
